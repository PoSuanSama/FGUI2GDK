# 工程质量门禁

## 编码前定义完成标准

将需求转化为可观察的验收标准：行为、支持模式、影响平台、错误处理、数据/配置影响和验证证据。明确非目标，避免局部修复演变成未经请求的框架重构。

## 保持兼容性

将以下内容视为兼容性边界：

- 公共 C# API 和程序集引用；
- 网络消息、操作码范围、MemoryPack/Proto 契约；
- Luban 结构、ID、表名、字段默认值和输出格式；
- 序列化字段、枚举值、预制体/场景引用、存档数据和缓存键；
- 资源路径、UI/Entity ID、分组，以及 AssetBundle/资源规则。

对已批准的破坏性变更，提供版本控制或迁移方案、混合版本行为、回滚和清理步骤。绝不静默重新解释已有数据。

## 管控依赖与工具链

- 添加包之前，优先使用现有框架能力。
- 在 `manifest.json`、`packages-lock.json` 和相关项目文件中以一致方式固定或锁定版本。
- 审查许可证、维护状态、目标兼容性、AOT/IL2CPP 支持、传递依赖、二进制大小和安全状况。
- 不要将包升级混入无关功能变更。
- 重新生成并审查锁文件；不要手动编辑锁文件来掩盖未解决的包状态。

## 保护秘密信息和不可信数据

- 绝不提交凭据、令牌、私钥、签名文件、包含真实秘密的连接字符串或生产用户数据。
- 从日志、截图、测试夹具和最终回复中隐去令牌、账户标识符和个人数据。
- 在信任边界验证路径、URL、文件名、命令、配置值和网络载荷。
- 不要使用不可信字符串拼接 Shell 命令；传递结构化参数。
- 除非已明确落实安全措施，否则不要把管理、调试或仅限 Editor 的能力带入运行时/Player 构建。

## 为诊断而设计

- 在负责处理失败的边界仅记录一次可操作上下文。
- 避免在每层调用栈重复记录，也不要吞掉异常。
- 记录稳定标识符和状态转换，不要记录秘密信息或完整载荷。
- 转换失败时保留原始异常/原因。
- 对间歇性缺陷添加有边界的诊断探针，随后移除，或明确将其保留为受支持的可观测能力。

## 控制性能预算

考虑 CPU、主线程停顿、分配/GC、GPU/过度绘制、内存驻留、网络流量、磁盘/缓存增长、加载时间和构建大小。性能结论必须使用 Profiler 证据。建立基线，并在变更后重复同一场景。

## 保持操作可逆

- 将破坏性生成和构建输出清理限制在明确范围内，并提前披露。
- 仅当项目已有归属和移除流程时，才使用功能/配置开关。
- 迁移操作必须定义备份/回滚和幂等性。
- 运行时服务必须定义超时、取消、重试/退避、重复请求行为和关闭清理。

## 保持文档同步

开发环境、生成流程、公共 API、资源工作流、配置或构建/发布行为变化时，更新相关 `Book/` 文档。记录原因和不变量；底层细节由源码和生成结构承载。

## 审查 AI 特有失误

交接前明确检查：

- 是否根据记忆而非当前源码进行编辑；
- 是否虚构 Bridge 命令或参数；
- 是否只改了生成输出而没有修改来源；
- 是否将工具命令成功误认为运行时行为正确；
- 是否用大范围格式化或重新导入噪声掩盖真实差异；
- 测试是否只验证了实现形态；
- 是否复制了旧版 GDK/AIBridge 中已过时的注释或文档；
- 是否意外包含、还原或格式化了用户变更。
