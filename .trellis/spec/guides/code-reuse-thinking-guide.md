# GDK Code Reuse Guide

## Search Before Adding

Use `rg` to find the concept, base type, lifecycle method, attribute, generated ID, and adjacent feature before creating code. In particular, search these established extension surfaces:

- GameHot bases and helpers under `Unity/Assets/Scripts/Game/Hot/`.
- ET component/system patterns under `Unity/Assets/Scripts/Game/ET/Code/` and `DotNet/`.
- UGF integrations under `Unity/Assets/Scripts/Game/ET/Loader/UGF/`.
- Containers and awaitable extensions under `Unity/Assets/Scripts/Game/Container/` and `Entity/`.
- Generators and analyzers under `Share/` and `Tools/`.

## Decide Whether To Reuse

- Follow an existing lifecycle/base class when behavior belongs to the same subsystem.
- Extend a local helper when it removes repeated error-prone behavior without widening dependencies.
- Keep one-off, obvious behavior local; do not create a utility for a trivial single call.
- Prefer generator inputs and templates when repetition is generated by design.
- Prefer project extension points over edits in `Unity/Assets/Scripts/Library/`.

## Typical Duplication Risks

- Reimplementing UI/entity open/show or resource loading instead of typed `GameEntry`/container APIs.
- Copying ET state and behavior into one class instead of using Model plus System.
- Defining numeric UI/entity/scene IDs outside Luban-generated definitions.
- Repeating cancellation/event cleanup rather than following the owning container or lifecycle base.
- Implementing the same feature in ET and GameHot without a two-mode requirement.

## Check Before Handoff

- Search confirms all call sites and constants were considered.
- The chosen abstraction stays inside the correct assembly/runtime boundary.
- No generated or vendor file became the convenient source of truth.
- Reuse did not introduce a broad dependency or obscure lifecycle ownership.
