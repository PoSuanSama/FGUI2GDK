# Unity Components, UI, And Entities

## GameHot

GameHot UI logic is a `IFairyUIPresenter` implementation marked with `[FairyUIPresenter(UIFormId.X)]` (scanned by `HotEntry.InitializeFairyGUI()`). Views are official FairyGUI bindings (`Game.FairyGUI.Package1`), obtained in `OnViewReady` from the context; GF lifecycle methods (`OnOpen`/`OnClose`/`OnPause`/`OnResume`/`OnCover`/`OnReveal`/`OnRefocus`) come from the unified GF host.

Entity logic and data remain separate under `Entity/EntityLogic/` and `Entity/EntityData/`. Open/show forms and entities through `FairyUIFormService`/`GameEntry` using generated IDs, never hard-coded asset paths or numeric IDs.

## ET Client/View

State components live in ModelView and declare ownership/lifecycles, for example:

```csharp
[ComponentOf(typeof(UIComponent))]
public class FairyDemoFormComponent : FairyUIFormComponent,
    IAwake, IUGFUIFormOnOpen, IUGFUIFormOnClose { }
```

Behavior lives in a matching HotfixView `static partial` system with `[EntitySystemOf]`, dispatched through `EntitySystemSingleton.TypeSystems` with `[UGFUIFormSystem]` methods (see `FairyDemoFormComponentSystem.cs`). UI ID → Component factories are registered in `FairyUIFormComponentRegistry` via `FairyGUIBootstrap.InitializeAsync()`. `UIComponent` owns all FairyGUI forms (per-open CTS, owned serial/CTS); Destroy cancels pending opens and closes owned serials.

## Avoid

- Putting mutable behavior into ET component data classes.
- Referencing `UnityEditor` from runtime assemblies.
- Bypassing official FairyGUI bindings with fragile hierarchy searches.
- Editing generated `*Id.cs`, `*.json` descriptors, or `<auto-generated>` files directly.
- Creating a second page stack beside GF `IUIManager`; everything goes through `FairyUIManager`.
